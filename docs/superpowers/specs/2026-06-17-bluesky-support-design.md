# Bluesky Support — Design Spec

**Date:** 2026-06-17
**Branch:** `decouple` (continues the backend-abstraction + multi-account work)
**Status:** Approved design, ready for implementation planning

## Goal

Let users add a Bluesky account alongside their Lemmy account(s) and run the
Stakswipe swipe loop against it. Bluesky has no Lemmy-style sort; instead it has
*feeds* (Following, Discover, and the user's pinned custom feeds), which surface
in the existing sort-dropdown position. Scope for this version is the **core
swipe loop**: browse feeds, swipe-right to like, read the reply thread inline,
open a post detail, and view an author's profile.

## Background

The app already has everything needed to host a second backend:

- `src/lib/api/backend.ts` — neutral `Backend` interface with nine sub-services
  (`auth`, `feed`, `posts`, `comments`, `sources`, `users`, `notifications`,
  `search`, `media`).
- `src/lib/api/capabilities.ts` — each backend self-describes via `Capabilities`
  (login fields, feed options, comment sorts, flags like `canDownvote`).
- `src/lib/api/registry.ts` + `src/lib/api/backends/index.ts` — backends register
  by id; `createBackend(session)` builds the active one.
- `src/lib/accounts.ts` + `src/lib/AccountsContext.tsx` — multi-account registry,
  active-stak pointer, aggregated stak selector.

Adding Bluesky means writing a new adapter under
`src/lib/api/backends/bluesky/`, registering it, and making a few small UI
adjustments for "no sorts" and "no communities." The `Backend` interface itself
does not change.

**New dependency:** `@atproto/api` (isomorphic; uses `fetch`, works in the
browser).

## Non-goals (this version)

Out of scope, deferred to later increments:

- Posting, replying, comment voting/editing/deleting
- Notifications inbox
- Search
- Reporting and media upload
- Bookmarks / saved posts (no public AT Protocol API)
- Communities / "sources" (no Bluesky analog)
- OAuth login (app passwords only for now)
- Anonymous (logged-out) Bluesky browsing

## Architecture

### File layout (new)

```
src/lib/api/backends/bluesky/
  index.ts        # createBlueskyBackend(session, opts) — assembles the Backend
  agent.ts        # build/resume an @atproto/api Agent from session.data
  session.ts      # BlueskySessionData type + helpers; feed list from session
  mappers.ts      # AT Protocol views ↔ neutral domain types
  mappers.test.ts
  capabilities.ts # buildBlueskyCapabilities(session) — dynamic feedOptions
  capabilities.test.ts
  feed.ts         # FeedService (getTimeline / getFeed routing)
  feed.test.ts
  posts.ts        # PostService (get, getByPermalink, vote=like/unlike) + stubs
  comments.ts     # CommentService (list via getPostThread) + stubs
  users.ts        # UserService (get=getProfile, getPosts=getAuthorFeed) + stubs
  stubs.ts        # shared "not supported in v1" throwers / no-ops
```

### Registration

`src/lib/api/backends/index.ts` `registerBackends()` gains a `bluesky`
registration mirroring the Lemmy one:

```ts
if (!hasBackend('bluesky')) {
  registerBackend('bluesky', (session) =>
    createBlueskyBackend(session, {
      persistSession: (data) => updateSessionData(session.id, data),
    }),
  );
}
```

`updateSessionData` is a new helper in `accounts.ts` (see Auth & session).

## Auth & session (app password)

### Login fields (capabilities)

```ts
loginFields: [
  { key: 'identifier', label: 'Handle or email', type: 'text', required: true,
    placeholder: 'you.bsky.social', autoCapitalize: false },
  { key: 'appPassword', label: 'App password', type: 'password', required: true,
    placeholder: 'xxxx-xxxx-xxxx-xxxx' },
]
```

The service endpoint defaults to `https://bsky.social` (no field). App passwords
are generated by the user at *Settings → App Passwords* on bsky.app.

### `BlueskySessionData`

```ts
interface BlueskySessionData {
  service: string;      // 'https://bsky.social'
  did: string;
  handle: string;
  accessJwt: string;
  refreshJwt: string;
  feeds: BlueskyFeed[]; // resolved at login from preferences
}

interface BlueskyFeed {
  id: string;           // 'following' | <feed at-uri>
  label: string;        // 'Following' | 'Discover' | pinned feed display name
}
```

### `auth.login(credentials)`

1. `const session = new CredentialSession(new URL('https://bsky.social'))`
2. `await session.login({ identifier, password: appPassword })`
3. Build an `Agent(session)`; call `getProfile({ actor: session.did })` → map to
   neutral `viewer`.
4. Resolve the feed list (see below) and store it.
5. Return a neutral `Session`:
   - `id = 'bluesky:' + handle.toLowerCase()` (stable across re-login)
   - `backendId = 'bluesky'`
   - `viewer` = mapped profile
   - `data` = `BlueskySessionData`

### Feed resolution at login

Call `agent.app.bsky.actor.getPreferences()` (or `agent.getPreferences()`) and
read the saved-feeds preference. Build `feeds`:

- Always prepend `{ id: 'following', label: 'Following' }`.
- For each **pinned** saved feed of type `feed`, add
  `{ id: <at-uri>, label: <display name> }`. Display name comes from
  `getFeedGenerators()` for the pinned URIs (one batched call); fall back to the
  URI's rkey if a generator lookup fails.
- Discover is itself a pinned feed for most accounts; if not present, append the
  well-known Discover feed URI so every account has at least Following +
  Discover.

This makes the feed list a snapshot taken at login. Re-logging in refreshes it.
(Live refresh of pinned feeds is a future enhancement.)

### Token rotation & persistence

AT Protocol refresh tokens rotate on use. The backend is rebuilt per session
(via `useMemo` in `AccountsContext`), so refreshed tokens must be written back or
sessions break after the access token expires across reloads.

- The Bluesky backend builds its `CredentialSession` with a `persistSession`
  callback. On `update`/`create` events it calls `opts.persistSession(newData)`.
- New helper in `src/lib/accounts.ts`:

  ```ts
  export function updateSessionData(
    sessionId: string,
    data: Partial<Session['data']>,
  ): void {
    const accounts = loadAccounts();
    const idx = accounts.findIndex((a) => a.session.id === sessionId);
    if (idx < 0) return;
    accounts[idx] = {
      ...accounts[idx],
      session: { ...accounts[idx].session,
        data: { ...accounts[idx].session.data, ...data } },
    };
    saveAccounts(accounts);
  }
  ```

- The backend factory in `registerBackends()` wires `persistSession` to
  `updateSessionData(session.id, …)`. This keeps token persistence decoupled
  from React.

### `agent.ts`

`buildAgent(session, persist)` reconstructs a `CredentialSession` from stored
tokens via `resumeSession({ did, handle, accessJwt, refreshJwt, active: true })`,
attaches the `persistSession` callback, and returns an `Agent`. The agent
auto-refreshes using the stored `refreshJwt`.

## Feeds → the sort dropdown

The user chose to surface Bluesky feeds in the sort-dropdown position rather than
as staks.

- **Staks:** `listStaks()` returns a single stak `{ id: 'home', label: 'Home' }`,
  so each Bluesky account is one entry in the aggregated account/stak selector.
- **Feeds:** the sort dropdown is already driven by
  `backend.capabilities.feedOptions` (`HeaderBar.tsx:54,143`). For Bluesky,
  `feedOptions` is built per-session from `session.data.feeds`:
  `feedOptions = feeds.map(f => ({ id: f.id, label: f.label }))`.
- **Routing:** `feed.getTimeline({ feedId, stakId, cursor })` ignores `stakId`
  and routes on `feedId`:
  - `feedId === 'following'` → `agent.getTimeline({ cursor, limit })`
  - otherwise → `agent.app.bsky.feed.getFeed({ feed: feedId, cursor, limit })`
  - Each returns `{ feed: FeedViewPost[], cursor }`; map to neutral `Post[]` and
    set `nextCursor = res.cursor ?? null`.
- **`getSourceFeed` / `getSavedPosts`:** not used for Bluesky in v1. `getSourceFeed`
  throws (no communities); `getSavedPosts` returns an empty page (`hasSavedPosts`
  is false, so the saved UI is gated off).

### Default-feed fallback (FeedStack)

`settings.defaultFeedId` defaults to a Lemmy sort (e.g. `Active`), which is not a
valid Bluesky feed id. `FeedStack` chooses the initial feed by checking whether
`settings.defaultFeedId` exists in `backend.capabilities.feedOptions`; if not, it
uses `feedOptions[0].id` (Following). Same logic protects the sort-dropdown's
current selection when switching the active account between backends.

## Type mapping

### Post (`FeedViewPost` / `PostView` → `Post`)

- `id = encodeBlueskyId(uri, cid)` → `'<at-uri>|<cid>'`. The cid is required to
  like/unlike, so it travels inside the id like Lemmy's `localId|apId`.
- `author` = mapped `ProfileViewBasic`.
- `title` = undefined (Bluesky posts have no title).
- `body` = `record.text`.
- `mediaUrl` = first image/external thumb from `embed`, when present.
- `externalUrl` = external embed uri, when present.
- `nsfw` = false (label handling out of scope).
- `publishedAt` = `record.createdAt` (or `indexedAt`).
- `permalink` = `https://bsky.app/profile/<handle>/post/<rkey>`.
- `counts.score` = `likeCount`; `counts.comments` = `replyCount`.
- `viewer.vote` = `viewer.like ? 1 : 0`; `viewer.saved` = false.
- `source` = benign placeholder (see "no communities").

### Comment (`getPostThread` → `Comment[]`)

`comments.list(postId)` calls `agent.getPostThread({ uri, depth })`, then
flattens the `ThreadViewPost.replies` tree depth-first into `Comment[]`:

- `id = encodeBlueskyId(reply.uri, reply.cid)`
- `postId` = the root post id
- `parentId` = parent reply's encoded id (null at top level)
- `depth` = tree depth
- `author`, `body = record.text`, `publishedAt`, `permalink`, `counts.score =
  likeCount`, `viewer.vote = viewer.like ? 1 : 0`
- Blocked/not-found thread nodes are skipped.

`opts.sortId` and `opts.sourceHandle` (passed by `PostCard`) are ignored.

### User (`ProfileView` → `User`)

- `id = did`
- `handle` = Bluesky handle (e.g. `alice.bsky.social`) — note: no `@instance`
  suffix, unlike Lemmy
- `displayName`, `avatar`, `bio = description`
- `profileUrl = https://bsky.app/profile/<handle>`

`users.get(handle)` → `getProfile`; `users.getPosts(handle, {cursor})` →
`getAuthorFeed`. `users.getComments` returns an empty page (out of scope);
`users.block` is a no-op.

### "No communities"

`Post.source` is required by the neutral type but has no Bluesky meaning.

- Add a `hasSources: boolean` flag to `Capabilities` (Lemmy: `true`, mock:
  `true`, Bluesky: `false`).
- The mapper fills `source` with a benign placeholder so the type is satisfied
  (id = author did, handle/name = author handle, zeroed counts).
- `PostCardShell.tsx` renders the **author-only** header when `!hasSources`:
  skip the `CommunityAvatar` + `c/<source>` row; show the author identity that
  is otherwise the secondary line. Lemmy is unchanged (`hasSources: true`).
- Other surfaces that render `c/<source.name>` (ProfilePage, SearchPage,
  SavedPage) are out of the core swipe loop and are not reachable for Bluesky in
  v1 (search/saved gated by capabilities; profile post lists show author posts
  without a community chip — verified during implementation, hidden behind
  `hasSources` if needed).

## Capabilities (Bluesky)

```ts
{
  canDownvote: false,
  canBrowseAnonymously: false,
  hasNsfwFlag: false,
  hasSavedPosts: false,
  hasSources: false,
  feedOptions: <dynamic from session.data.feeds>,
  commentSortOptions: [],
  sourceNoun: '',
  displayName: 'Bluesky',
  icon: '🦋',
  loginFields: [ identifier, appPassword ],
}
```

Built by `buildBlueskyCapabilities(session)` so `feedOptions` reflects the
logged-in account's feeds. The anonymous/placeholder session (used by
`BackendSelectPage` and `DynamicLoginPage` before login) yields the static login
fields with an empty `feedOptions`.

## Sub-services summary

| Service | Method | Bluesky v1 |
| --- | --- | --- |
| auth | login / logout | implemented / no-op |
| feed | getTimeline | implemented (following + getFeed) |
| feed | getSourceFeed / getSavedPosts | throws / empty page |
| posts | get / getByPermalink | implemented |
| posts | vote | like / unlike (vote 1 = like, 0/-1 = unlike) |
| posts | save / report / delete / create | stub throws |
| comments | list | implemented (getPostThread) |
| comments | vote / create / edit / delete / report | stub throws |
| sources | get / subscribe / block | stub throws / no-op |
| users | get / getPosts | implemented |
| users | getComments / block | empty page / no-op |
| notifications | * | stub (unreadCount → 0, list → empty) |
| search | * | stub (empty page) |
| media | uploadImage | stub throws |

Stubs that throw use a clear message (e.g. `'Not supported on Bluesky yet'`) so
any unexpected call surfaces loudly in development. Stubs that the UI may call
opportunistically (e.g. `notifications.unreadCount`) return benign empty values
so the header badge simply shows nothing.

## UI changes

All small and behind capability flags so Lemmy is untouched:

1. `src/lib/api/capabilities.ts` — add `hasSources: boolean`.
2. `src/lib/api/backends/lemmy/index.ts` + `mock/index.ts` — set
   `hasSources: true`.
3. `src/components/PostCardShell.tsx` — author-only header when `!hasSources`.
4. `src/components/FeedStack.tsx` —
   - replace the hardcoded `SORT_OPTIONS` pill row (the "you've seen everything"
     screen) with `backend.capabilities.feedOptions`;
   - initial-feed selection falls back to `feedOptions[0].id` when
     `settings.defaultFeedId` is not a valid option for the active backend.
5. `src/lib/accounts.ts` — add `updateSessionData(sessionId, data)`.
6. `src/lib/api/backends/index.ts` — register `bluesky`.

`DynamicLoginPage` and `BackendSelectPage` already render any backend's
`loginFields` and list any registered backend, so the add-account flow needs no
changes.

## Swipe semantics on Bluesky

- **Swipe right** → `posts.vote(id, 1)` → like.
- **Swipe left** → with `nonUpvoteSwipeAction === 'downvote'`, `FeedStack` calls
  `posts.vote(id, -1)`. Bluesky has `canDownvote: false`; `vote(-1)` maps to
  **unlike** (remove like if present), never a downvote. Effectively swipe-left
  is "skip" and clears any like.
- **Swipe down** → undo (unchanged, client-side).

## Risks & mitigations

- **Token rotation:** handled by `persistSession` → `updateSessionData`.
- **`@atproto/api` bundle size:** acceptable; tree-shaken via Vite. Flagged for
  review if it noticeably impacts the PWA bundle.
- **Pinned-feed display names:** one batched `getFeedGenerators()` call at login;
  fall back to the URI rkey on failure so login never blocks on it.
- **Handle format divergence:** Bluesky handles have no `@instance` suffix; code
  that splits `handle` on `@` (PostCardShell `srcName`/`authorName`) must degrade
  gracefully — verified by the author-only path and a mapping test.
